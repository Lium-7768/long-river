# 长河 · 中国通史知识图谱 — 需求文档

> 最后更新：2026-10-09
> 配套文档：[数据模型](./data-model.md)

## 1. 项目定位

以中国通史为内容的知识图谱站点，用文字与图表讲清历史。

核心原则：**所有实体平权**。人物、家族、官职、作品、事件、政权各自拥有独立页面，彼此自由互链。「朝代 → 人物 → 作品」只是默认引导路径，不构成数据约束。

这条原则的来由是三个跨朝代的维度装不进树状结构：

- **家族跨朝代** — 琅琊王氏自汉延续至唐，陇西李氏横跨北朝、隋、唐。若家族挂在朝代下，同族成员会被割裂到不同子树。
- **官职跨朝代且语义漂移** — 尚书令在汉、唐、宋是三种不同的职位，宋代基本为虚衔。不能用一张全局官职表。
- **姓氏是独立浏览轴** — 不属于任何朝代。

### 范围

首期内容做**宋**：北宋（960–1127）、南宋（1127–1279），并列辽（907–1125）、金（1115–1234）、西夏（1038–1227）。

数据 schema 按全朝代通用设计，首期只填宋段内容。

选宋而非唐的理由：

1. CBDB 起源于宋代人物数据库，宋的结构化数据覆盖密度远高于其他朝代。
2. 河道拓扑能跑满四种形态 —— 北宋/辽/西夏三股并行 → 1127 靖康之变主流断折南移 → 南宋/金并行 → 1279 终止。
3. 六条轴全部有充实内容：科举世家（家族）、二府三司（官职）、宋词与科技著作（作品）、变法与党争（事件）、理学师承（学派）。
4. 视觉语言可从宋代自身生成，不需凭空编造「历史感」。

## 2. 导航层级

### L0 — 长河总览

3D 河道场景。滚动驱动相机沿河漫游，朝代为河段，并立政权为支流。

宋段看点：北宋/辽/西夏三股并行 → 1127 主流断折南移 → 南宋/金并行至 1279。

河段长度按 `sqrt(年数)` 压缩，避免秦（15 年）这类短命政权小到无法点击，同时保留相对长短感。

### L1 — 政权页

点击河段，镜头推进，河段展开为该政权内部视图。详见 §3。

### L2 — 实体页

六类实体（+ 附加实体）的详情页，各自独立静态路由：

```
/polity/northern-song
/person/su-shi
/clan/meishan-su
/office/song-tongzhi-shumenxia-pingzhangshi
/work/nian-nu-jiao-chi-bi-huai-gu
/event/jingkang-incident
/surname/su
/era/yuanfeng
/institution/song-shumiyuan
/school/luo-xue
/place/bianjing
```

### L3 — 自由跳转

任意实体间互链。例：王安石 ↔ 司马光（政敌）、苏洵 ↔ 苏轼 ↔ 苏辙（家族）、同一官职的历任者列表、《念奴娇·赤壁怀古》↔ 苏轼 ↔ 黄州 ↔ 乌台诗案。

### 降级路径

全站提供 2D 纵向时间轴版本，承载：无 WebGL 环境、搜索引擎爬虫、`prefers-reduced-motion` 用户、低端移动设备。

此版本为 SEO 本来就必须存在，不是额外成本。

## 3. 政权页 — 时代断面

政权页的职责与实体页根本不同：实体页讲**个体**，政权页讲**断面**——那个时代的制度、经济、思想是什么样。

它不应是一个人物索引页。六条轴都要在此有汇总入口。

### 3.1 概览

起止年、都城（汴京 → 临安）、疆域概述、历史分期、同期并立政权。

### 3.2 帝王纪年轴

两宋十八帝（北宋九帝、南宋九帝）的在位区间。年号带（数十个年号，构建期从数据生成，不手工维护）。

### 3.3 年表

**分类**：政治 / 军事 / 制度 / 经济 / 文化 / 对外 / 灾异

**分级**：王朝级 / 朝廷级 / 地方级

时间轴默认只渲染王朝级事件，可逐层展开。约 300 条事件若不分类分级即不可读。

**事件密度带** —— 时间轴下方的密度条，熙宁年间与靖康前后的事件密集会自然凸显，无需文字说明。密度本身是信息。

### 3.4 因果链

事件之间建 `causes` / `consequenceOf` 有向边，生成事件链视图。

北宋主脉：

```
澶渊之盟 (1005) → 岁币 + 养兵 → 财政积弊
  → 庆历新政 (1043–1045，失败)
  → 熙宁变法 (1069)
  → 元祐更化 (1085)
  → 新旧党争反复
  → 徽宗朝政失序
  → 靖康之变 (1126–1127)
```

这条链是北宋史的叙事骨架，比按年排列的列表有价值得多。

### 3.5 横切面视图

**本项目最具价值的功能之一，且数据成本为零** —— 完全从已有的 `Appointment`、生卒年、作品年份计算得出，不需额外撰写内容。

选定任意一年，呈现该年全景：在世人物、各要职任职者、正在发生的事件、新问世的作品。

以 1080 年（元丰三年）为例：

| 维度 | 内容 |
|---|---|
| 苏轼 | 乌台诗案后贬黄州 |
| 王安石 | 已罢相，居江宁 |
| 司马光 | 在洛阳修《资治通鉴》 |
| 沈括 | 在任，后撰《梦溪笔谈》 |
| 辽 | 道宗在位 |

一屏之内，整个时代的人物关系与政治格局立起来。此视图把六条轴串在一起，是单个实体页做不到的。

### 3.6 制度总览

二府三司（中书门下 / 枢密院 / 三司）、台谏、路州县三级地方、**官职差遣分离**（宋代官制核心特征：官阶、职名、差遣三者分离）。

作为 Office 与 Institution 轴的入口。

### 3.7 选官

科举定型、糊名与誊录、殿试，取士人数趋势图。

通向 Person 与 Clan —— 宋代门阀式微、科举世家兴起，是与唐的根本区别。

### 3.8 经济

交子（北宋四川）与会子（南宋）、市舶司与海上贸易、商税超越农税、城市化（汴京人口规模）。

**此维度不可省略。** 宋的辨识度很大程度在此 —— 纸币、海外贸易、商业税收结构、城市化。缺了它，宋只剩「打不过辽金但诗词好」的刻板印象。

数据处理规则见 §8.3。

### 3.9 思想

理学师承谱系：濂溪（周敦颐）→ 二程（程颢、程颐）→ 朱熹；关学（张载）、洛学、新学、蜀学分野。

升格为独立的 `School` 轴 —— 师承结构与亲属谱系同构（均为有向图），但语义完全不同。

### 3.10 科技

活字印刷（毕昇）、指南针应用于航海、水运仪象台（苏颂）、《梦溪笔谈》。

通向 Work 轴。

### 3.11 对外关系

澶渊之盟（1005）、庆历和议（1044，宋夏）、绍兴和议（1141）。各带岁币数额、边界划定、存续期。

与河道并流形态绑定 —— 盟约存续期对应支流平行段。

### 3.12 地理

汴京 → 临安的都城南迁、经济重心南移、燕云十六州的战略地位。

通向 Place 轴与地图模块。

## 4. 实体页内容

### 人物 Person

姓名字号、生卒、郡望与所属家族、谱系中的位置与族内成员、入仕途径（科举 / 门荫 / 荐举）、仕途迁转全程、代表作品、参与事件、人际关系（师生 / 同僚 / 政敌 / 姻亲）、生平长文。

### 家族 Clan

姓 + 郡望构成身份、活跃年代跨度、门第等级、分支、谱系树、成员列表。

独立顶层实体，不挂在任何政权下。

### 官职 Office

名称、品阶、所属机构、职掌、历任者列表、前后朝沿革链。

按政权作用域存储 —— 同名官职在不同政权是不同条目，以 `successorOf` 相连。

由此可生成三种视图：人物仕途轨迹（最能体现一生起落）、官职历任者列表、制度演变。

### 作品 Work

类型（诗 / 词 / 文 / 著作 / 画作 / 工程 / 发明）、作者、创作年份、原文或摘录、创作背景、关联人物与事件。

### 事件 Event

年份或区间、地点、参与人物、起因、经过、影响、相关作品、因果边。

### 姓氏 Surname

得姓源流、郡望列表、历代名人分布。与 Clan 一对多。

### 年号 Era

起止年、所属帝王、改元缘由。年号 ↔ 公元对照是贯穿全站的工具 —— 史料全用年号纪年，「元丰三年 / 1080」的双轨显示必须随处可用。

### 机构 Institution

Office 的父级。职掌、沿革、下属官职列表。使官职轴可按机构导航。

### 学派 School

师承边、宗旨、代表人物、代表著作、与其他学派的分野。

### 地点 Place

历史地名与今地对照、作为事件与人物行迹的空间锚点、相关人物与事件。

### 变法 Reform

政策包，含多条具体措施（青苗法 / 募役法 / 保甲法 / 方田均税法等）。推行者、反对者、起止、成效与争议。

技术上可视为 Event 子类型，但熙宁变法牵动的人物与官职关系网极密，独立成实体更合适。

### 盟约 Treaty

缔约方、岁币数额、边界划定、存续期、后续影响。

## 5. 图表清单

| 图形 | 承载内容 | 布局算法 |
|---|---|---|
| 政权甘特图 | 朝代并立关系，分轨道 | 自定义 |
| 帝王在位轴 + 年号带 | 政权内部纪年 | `d3-scale` |
| 事件密度带 | 事件时间分布 | 直方 / 核密度 |
| 因果链图 | 事件有向关系 | DAG 分层 |
| 家族谱系树 | 含婚姻边，实为 DAG 非树 | `d3-hierarchy` + 自定义 |
| 人物关系力导向图 | 师生 / 同僚 / 政敌 / 姻亲 | `d3-force` |
| 仕途迁转图 | 按官品分层，看一生起落 | `d3-sankey` |
| 师承谱系图 | 学派传承 | `d3-hierarchy` |
| 时间序列 | 取士数、财政、人口、疆域面积 | `d3-shape` |
| 横切面全景 | 某一年的六轴快照 | 自定义 |
| 疆域地图 | 疆域变迁 | maplibre + CHGIS |

全站共用一套 `d3-scale` 时间比例尺与配色系统，保证十余种图形看起来属于同一体系。

绘制图表前须先执行 `dataviz` 规范，确保配色与无障碍一致。

## 6. 技术架构

### 架构铁律

**3D 只承载导航外壳，所有内容是浮在 Canvas 之上的 2D DOM。**

Canvas 内只有河流、支流、朝代标记、相机运动。人物生平、谱系、仕途、诗文全部是普通 HTML。

这不是妥协，是必须的：WebGL 中的文字没有文本选中、浏览器搜索、无障碍支持和 SEO。同时每个实体保留独立静态路由，3D 长河只是 `/` 的入口外壳 —— 爬虫、无 WebGL 环境、低端移动设备都能完整访问全站内容，3D 失效不影响可用性。

### 技术选型

| 层 | 技术 | 说明 |
|---|---|---|
| 框架 | Next.js App Router，全量 SSG | 内容静态，无需后端与数据库 |
| 3D | react-three-fiber + drei | `dynamic(..., { ssr: false })` 隔离，不污染静态渲染 |
| UI | Tailwind + shadcn/ui (Radix) | 需要可完全控制样式的无样式基元，而非一套既定设计语言 |
| 长文 | MDX | frontmatter 存结构化字段，body 存散文 |
| 校验 | zod | 构建期硬校验，数据错误不进产物 |
| 图表 | `d3-scale` / `d3-shape` / `d3-hierarchy` / `d3-force` / `d3-sankey` + 手写 SVG | 见下 |
| 动效 | framer-motion（2D 面板）/ R3F easing（相机） | 两套不混 |
| 搜索 | minisearch | 构建期生成索引，纯客户端 |
| 地图 | maplibre + CHGIS | 后期独立模块 |

**不使用图表组件库**（Recharts / ECharts）。理由：十余种图形各不相同 —— 谱系树带婚姻边实为 DAG、仕途图按官品分层、政权甘特图需处理并立轨道。这些均需定制，用组件库等于先接受其抽象再逐个破解。只取 d3 的计算模块，渲染自己写。

**不使用状态管理库**。URL 即状态。

### 3D 实现要点

- **河道曲线** —— `CatmullRomCurve3` 过控制点，河面为沿曲线挤出的 ribbon mesh。约 20 个政权 × 40 段细分，几何量可忽略。
- **相机** —— 滚动驱动 `curve.getPointAt(t)`，相机沿河漫游并 `lookAt` 前方。点击支流时切换至子曲线，easing 过渡。
- **水面不做写实** —— 不用反射折射。滚动法线贴图 + fresnel，整体走**青绿山水**风格化方向。既贴题，又比写实水便宜一个量级，且不与中文排版冲突。
- **标签** —— 用 drei `<Html>`，朝代名是真 DOM，不用文字网格（troika）。
- **降级** —— WebGL 检测失败或 `prefers-reduced-motion` → 落到 2D 纵向时间轴。

河道几何在**构建期**从数据算出，不在运行时布局。拓扑字段见[数据模型](./data-model.md)。

## 7. 视觉与排版

### 视觉语言

从宋代自身取材：

- **主色** —— 汝窑天青
- **排版结构** —— 宋版书的字面与版式比例
- **河面风格** —— 范宽、郭熙一路的青绿山水

### 中文排版

**这块比 3D 更容易做砸，且基本没有现成方案可抄。**

- **字体子集化是硬约束** —— Noto Serif SC 全集十余 MB，不能直接加载。构建期扫描全站实际使用字符生成子集。宋代人名与诗文含生僻字（如「頔」「頵」），须保证子集覆盖。正文倾向霞鹜文楷或思源宋体，标题用骨架更强的宋体。
- **诗词竖排** —— `writing-mode: vertical-rl`，现代浏览器支持良好。词牌 + 正文竖排居中，与散文段落明确区分。
- **中文不用斜体** —— CJK 斜体是机械倾斜，排版上是错误的。强调用字重、字号或专名线（`text-emphasis` / `border-bottom`）。
- **书名号《》** 正确使用。
- **年号与公元双轨** —— 「元丰三年（1080）」贯穿全站。
- **数字用衬线等宽**。

这些细节决定站点看起来是否懂行。

## 8. 数据管线

### 8.1 分工原则

**易错的结构化事实由 CBDB 保证，容错的散文交给 LLM。**

CBDB（中国历代人物传记资料库，哈佛，CC 授权）提供骨架：生卒年、郡望、亲属关系、官职任免、入仕途径。LLM 只填生平散文与事件叙述。

年份、亲属、官职这类 LLM 高错误率的字段，一律不由 LLM 生成。

### 8.2 ETL 流程

```
CBDB SQLite
  → 按政权筛出子集
  → 映射为本项目 schema
  → zod 校验
  → 生成 MDX 骨架（frontmatter 填满，body 留空）
  → LLM 填 body 散文
  → 产物进 content/_draft/
  → 人工抽检
  → 移入正式目录
```

表映射见[数据模型 §CBDB 映射](./data-model.md#cbdb-映射)。

### 8.3 争议数据处理规则

经济与人口的具体数字在史学界有争议（宋代人口峰值有 1 亿、1.2 亿等不同估算）。

**规则：此类数据必须标注出处与异说，不给单一确定值。** 数据结构上支持多估算值并列。

这也是 LLM 最容易编造的地方。

### 8.4 校验

- 生卒年与在位年交叉校验
- 任职年份须落在人物生卒区间内
- 亲属边双向一致性（构建期自动补全反向边）
- 作品标题对照权威索引
- 事件因果边无环检测
- 引用完整性：所有 slug 引用必须指向存在的实体

## 9. 待补功能

> 本节记录首轮设计评审中发现的缺口。分三级：**结构性**（现在不做，后续要重做数据）、**数据模型**（schema 层漏洞）、**体验层**（缺了只是打折）。每项标注期次。

### 9.1 结构性缺口

#### 检索索引层 —— 一期必须

现在只有一句「搜索用 minisearch」，未定义**搜什么**。中文历史检索的难点在于别名归一：

- 「东坡」须命中苏轼（别号）
- 「元丰三年」须命中事件、人物、年号页（年号 ↔ 公元换算）
- 「王安石 司马光」须命中两人关系
- 「汴梁」「东京」须命中汴京（地名旧名）
- 「辛未」须命中对应年份（干支）

**需要一个独立的别名索引层**：从 `Person.altNames`、`Place.altNames`、`Era.name`、`Surname` 等抽取所有别名，统一归一为「别名 → 实体 slug」的映射，随实体一同进 minisearch 索引。

这不是给 minisearch 加个字段，而是一层数据加工：别名来源分散在各实体，需在构建期聚合；年号 / 干支 / 公元换算需公共函数（见 §7）。

#### 全朝代河道拓扑 —— 一期必须

「长河」是核心卖点，但 `river` 拓扑字段目前**只定义了宋段五股**（北宋 / 南宋 / 辽 / 金 / 西夏）。秦至五代、元明清的 `stream` / `parent` / `lateralOffset` / `confluence` / `rupture` 全部未定。

「schema 按全朝代通用设计」只在字段层面成立，拓扑数据层面是空白。这是必做的数据工程：

- 逐个政权定 `lateralOffset`，保证并立政权在 Z 轴错开且不重叠
- 定 `parent` 分叉点（如三国归晋的 `confluence`、五代十国的多股并流）
- 定 `rupture` 断折点（如靖康之变、南宋覆亡）

未完成前，L0 长河只能显示宋段，其余河段缺位。

#### 遗址与文物 —— 二期

历史站的天然入口是「此地今日可见什么」。现有 `Place` 只有都城 / 州府 / 关隘 / 战场 / 其他五类，缺：

- **现存遗址与建筑** —— 今天仍可访问的地点（开封铁塔、应县木塔、泉州宋元码头）
- **文物** —— 现存实物及其收藏地（《清明上河图》藏故宫；关心的不是创作信息，而是「今日在哪、能不能看」）

作品讲创作，文物讲存世，两者是不同维度，需要独立字段或子类型。

#### 地图模块的最小可用版 —— 一期必须

地图现排在最后、依赖 CHGIS、工作量未评估，等于**未定义**。历史站无地图是硬伤。

须定一个 MVH（最小可用版），与后期疆域变迁解耦：

- **一期 MVH** —— 中国底图 + 人物行迹折线 + 事件点位。数据可从 `Person` 相关 `Place` 与 `Event.places` 推出，不依赖 CHGIS
- **后期** —— 疆域变迁（依赖 CHGIS 数据处理）

行迹是「本来就要」，疆域变迁是「锦上添花」，不能混在同一优先级里。

### 9.2 数据模型漏洞

#### `Person` 缺 `gender` —— 一期必须

现有 `Person` 无性别字段。影响面：

- 家族谱系树无法区分妻 / 女，姻亲边推导会错
- 女性历史人物浏览轴（李清照、武则天）无法独立组织

补一个字段成本为零，事后补要动全部内容数据。

#### 同名异人消歧 —— 一期必须

`Person` 只有 slug。历史上重名者众（两个李纲、多个张俊——北宋末张俊与南宋名将张俊须区分）。

需 `disambig` 字段（简短区分语，如「南宋初名将」），用于检索结果列表与互链时的消歧提示。

#### `Work` 缺存佚状况 —— 一期必须

`Work` 有 `year` / `place`，但无 `status`。史料中大量作品**已佚失**（仅存目录）、**部分存世**、或**伪托**。

不标存佚，用户以为能看到原文却看不到，是体验与可信度双重问题。需 `status: '存世' | '部分存世' | '已佚' | '辑佚' | '伪托'`。

#### 全局史料出处机制 —— 一期必须

**全站最根本的信任问题**：这条信息哪来的？

现在只有 `Series` 的 point 带 `source`，其余实体全无。须引入全局引用机制，二选一：

- 每实体带 `refs: Array<{ source: string; locator?: string }>`
- 独立 `Source` 实体，实体通过 slug 引用

**必须从 schema 一开始就带**，事后补要动全部内容文件。历史站不给出处，可信度为零。

#### 数据版本与溯源 —— 二期

CBDB 有版本、LLM 有模型版本、人工校订有编辑记录。改苏轼生卒年后，用户为何看到新值？

需 per-file `_meta: { source, generatedAt, reviewedBy, version }`。一期可先只记 `reviewedBy`，完整版本链排二期。

### 9.3 体验层缺口

#### 对比视图 —— 一期必须（成本极低）

两个人物、两个朝代、两个年号并列对比，是历史站高频需求。**数据成本为零** —— 全部是已有字段的并排渲染。文档此前完全未提。

#### 分享与 OG 卡片 —— 一期必须

知识图谱站一半价值在分享。`/person/su-shi` 分享到微信需有像样的 OG 卡片（姓名、生卒、一句话、配图）。文档此前零提及。需为每类实体定 OG 图生成规则。

#### 移动端策略 —— 一期必须（须明确决策）

此前只有一句「移动端适配」排在最后。但关键问题是：**3D 河道在手机上几乎不可用**。

须明确决策而非留到最后打磨：

- **方案 A** —— 移动端直接进 2D 纵向时间轴，不加载 3D（检测视口宽度 + WebGL 能力）
- **方案 B** —— 做触控专门优化的简化 3D

倾向方案 A：与已有降级路径复用，成本最低，且移动端本就不适合精细漫游。

#### 专题页 —— 二期

「士族兴衰」「理学北传」「海上丝路」「纸币流通」这类**跨实体、跨朝代的主题叙事**。

现在只有政权页与实体页，中间缺一层「专题」。本质上是一组手工编排的实体引用序列 + 导读散文。

#### 个人视角的时间旅行 —— 二期

「我在宋朝哪一年出生？那时谁在世、谁在任、发生了什么事？」—— 把横切面视图（§3.5）加一个年份输入即可玩化。横切面数据全部已有，只差一个 UI 入口。
